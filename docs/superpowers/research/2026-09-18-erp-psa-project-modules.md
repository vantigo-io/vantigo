# ERP/PSA project & planning models: a survey for Vantigo

Scope: Odoo (Project/Timesheets/Planning/Field Service), ERPNext, Microsoft Dynamics 365 Business Central (Jobs/Projects) and Project Operations, SAP Business One, Oracle NetSuite (native Project Management + SuiteProjects Pro/ex-OpenAir), Workday PSA, Scoro, Productive.io, Teamwork.com, Kantata (ex-Mavenlink), Harvest+Forecast, Float, Runn. All facts below are from official vendor documentation unless marked `[marketing]` (vendor feature/pricing pages, not help docs) or `[3rd-party]` (Wikipedia etc., used only for company history). `UNCERTAIN`/`NOT CONFIRMED` flags are preserved from the underlying research. This report synthesizes five parallel research passes; the full per-URL evidence trail for each fact lives in those passes and is summarized in Sources.

## 1. Hierarchy & milestones

| Product | Levels below Project | Milestone model | Dependencies |
|---|---|---|---|
| **Odoo** | Stages(kanban cols) → Tasks → multi-level Sub-tasks | Separate `project.milestone` object: name, deadline, %-of-SO-qty; tasks link to it; auto-"Reached" when linked tasks done | Task "Blocked by" m2m, **FS only**, sets successor status to Waiting; no critical path |
| **ERPNext** | Task, self-nesting via `Is Group`/`Parent Task` (arbitrary depth); no phase object | `Is Milestone` boolean flag on Task, no documented downstream effect | Child table of dependent tasks; completion-gate only, not scheduling |
| **BC Jobs/Projects** | Project → Project Tasks (flat, indented, Begin/End-Total groups) → Planning Lines; no subtask entity | No milestone entity/flag; convention = task + Billable planning line | **None documented** — no predecessor field anywhere; task dates derived from planning-line delivery dates |
| **D365 Project Operations** | Project → WBS (summary + leaf tasks, outline level, up to 10 levels, 3,000 tasks/project) | Two kinds: schedule milestone = zero-duration task (cosmetic); **Contract Line Milestone** = separate billing entity, task link "has no downstream impact" | Full PM-grade: FS/SS/FF/SF + lead/lag; `msdyn_iscritical` field exists |
| **SAP Business One** | Project → (optional recursive) Subprojects → Stages (5 fixed, renamable) → task rows | No milestone entity; nearest analogue = stage "Finished" checkbox + weighted Contribution % rollup | Finish-to-finish only, max 5 per row, can target a subproject; no lag, no critical path |
| **NetSuite native PM** | Project → parent(summary)/work tasks → milestones | Milestone = flag on task; "cannot have estimated hours, assignees, or FNLT constraints" | Full MS-Project semantics: FS/SS/SF/FF + Lag Days; **has critical path** in Gantt |
| **SuiteProjects Pro (ex-OpenAir)** | Project → Phases → Tasks → Milestones | Milestone is its own row type in the WBS | Drag-to-create dependencies in Gantt/Outline views |
| **Workday PSA** | `NOT PUBLICLY DOCUMENTED` — datasheet only names "project management" | Not public | Not public |
| **Scoro** | Project → Phases (optional, dynamic dates) → Tasks → Subtasks (1 level only) | Separate entity, pure **date marker** ("not containers for tasks") | FS/SS/FF/SF + lag/lead; changing a predecessor triggers automated rescheduling of dependents; no critical path confirmed |
| **Productive.io** | Client → Project → Folders(opt) → Task Lists(opt) → Tasks → Subtasks/TO-DOs (1 level) | **No milestone object**: "Key Tasks" for delivery dates; multiple Budgets/draft invoices for billing milestones | Blocking / Waiting on / Linked to; Gantt auto-reschedule skips weekends only (ignores individual leave calendars); no critical path confirmed |
| **Teamwork.com** | Client → Project → Task List (**mandatory**) → Task → Subtask | Separate entity with responsible person, attaches to task list(s); % auto-rolls from tasks but must be manually closed | Default FS + optional FF toggle; SS/SF not confirmed; **has Critical Path** (Gantt feature) |
| **Kantata** | Workspace → Story (up to 4 levels via parent_id) → Story Tasks (checklist items) | `story_type` = task/**milestone**/deliverable/issue — **same object as a task**, cheapest schema in the set; separately, **Billing Milestones** are a distinct invoicing object decoupled from delivery milestones | Separate object: FS/SS/FF/SF + lag (days); has critical-path button (KB, not independently re-verified) |
| **Harvest** | Client → Project → Task (flat; task = billing category only, no dates/assignee/status) | None | None |
| **Forecast** | Project → person/placeholder **assignments** over dates; no task breakdown (borrows Harvest task as a label only) | Decorative date marker on the Day view, no scheduling effect | None |
| **Float** | Client → Project → Phase → Task (thin: name+billable only, no dates/assignee) → **Allocation** (scheduling atom) | Name + date (optional range), attaches to project or phase; renders as coloured dot | None; "linked allocations" shift together but no true dependency graph |
| **Runn** | Client → Project → Phase (no task object at all; "designed for resource planning not task management") | Name, date, icon, note; no dependency/scheduling effect | None; hard rule: a person can only be assigned to **one phase per day** |

## 2. Time entries & rate resolution

| Product | Entry references | Approval workflow | Billable | Rate resolution (as documented) |
|---|---|---|---|---|
| **Odoo** | `account.analytic.line` + project/task/employee | Access-level based (No/Own/All/Admin); Grid "Validate"; thin docs, lock dates only in marketing | Computed `timesheet_invoice_type`, driven by whether an SO line resolves | Per-project mode: **Task rate** (task's own SO line) / **Project rate** (one SO line) / **Employee rate** (per-employee map, customer-matched, else task, else project) |
| **ERPNext** | Timesheet→Task/Project (both optional) + Activity Type | Save→Submit only; multi-level needs generic Workflow doctype (no built-in approver role) | `Bill` checkbox; Billing Hours ≠ worked hours | (1) Activity Cost (employee×activity type) → (2) Activity Type default → (3) manual edit. No project/customer/task rate. |
| **BC Jobs** | Time Sheet line → Project + Project Task, Work Type Code | **Open→Submitted→Approved/Rejected→Reopen**; approver = resource-card approver or Project "Person Responsible", selected by a 3-way setting | "Chargeable" copied from line | 3 project-specific price tables (Resource/Item/G-L Account Prices, keyed by task+work type) override resource-card prices, on top of a generic "lowest price, highest discount" engine. **No single published precedence table.** |
| **D365 Project Operations** | Time Entry → task/summary/project level, Role, Type | **Draft→Submitted→Approved/Returned**, actuals created **at approval**, Recall reverses (financial impact); Delegation supported | 3-value: Chargeable/Non-chargeable/Complimentary, computed from task×role×category×contract-line truth table, **editable at invoice time** | Explicit, ordered: date+currency picks price list → match Role+Resourcing Company+Resourcing Unit "in order of priority", nulls last; cost side has a **progressive dimension-dropping fallback** to 0 |
| **SAP B1** | Time Sheet row → Financial Project + **Stage** (not task) | **None documented** (only employee-absence approval exists) | Duration split: enter Non-Billable Time, system derives Effective/Billable | Single-level: Activity Type → default Labor Item → item price. No rate-card hierarchy. |
| **NetSuite native PM** | Time entry → Customer:Project, Case/Task/Event, service item | Approve Time page; "time must be entered, marked billable, **and approved** to be billed"; Approve-Automatically toggle | Billable requires a service item | Task override → service-item billing class → employee billing class → price-level price → employee default. Charge-based: Employee/Service/Billing-Class rate cards, else employee default. |
| **SuiteProjects Pro** | Timesheet grid → project + task/phase | Submit/Approve tab, per-entry accept/reject, statuses To Approve/Open/Submitted/Rejected/Approved | Task Type ≠ billing eligibility — **"Non-billable task" checkbox** controls it | **Global mode switch** (not a chain): Service / Service+Customer / Employee / Employee+Project / Customer+Project / **Project Billing Rules** (recommended). Cost from Job Codes. |
| **Workday PSA** | Not public beyond "entering and approving multiple projects at once" | Exists, mechanics not public | Not public | Not public |
| **Scoro** | Task (**required** — no project-only entry) + Activity Type | **Timesheet** (weekly grid submission) + separate **Time locking** (supervisor confirm/lock; "Confirm time entries" perm gates billing) | Default billable on one-off/retainer projects, overridable | Two alternative *methods*: Role-based (role default, **project-level override wins**) or Service-based (person-agnostic). No documented precedence when both could apply; no customer-tier rate. |
| **Productive.io** | Time entry → Service (**anchor for rate/budget**), Task optional, Deal/Budget, or a time-off event | **Draft→Submitted→Pending→Approved/Rejected**; only approved time counts toward budget/profitability; deal-stage time stays non-billable regardless | Billable = eligible; **Recognized** = actually chargeable (capped at budgeted qty for fixed-price) — explicit distinction | Per-budget *mode*: Person Rate / Service Rate / Single Billable Rate. Cost: **deal-specific override overrides org-wide default**; overhead added on top, differs for internal vs client budgets. |
| **Teamwork.com** | Project (**required**), Task optional (blank = project-level time) | **Unsubmitted→In review→Approved**, scoped per-user approvers, locks on approval, re-open request flow | Per-entry "Mark as billable" checkbox, project default | **Most explicit chain of all 16 products**: Project rate (per-user/project) > Client role rate > standard Role rate > user's site default. **Cost rate always from site-wide cost rate**, bypasses hierarchy. Manual edit converts entry to a project rate. |
| **Kantata** | Time Entry → Story(task), Role; rate & cost snapshotted onto entry | **Timesheet Submissions**, 1/project/week, states new→approved/rejected/cancelled; identical pattern applied to Expense Report Submissions | Flags at 4 levels: Time Entry, Story, Expense, Expense Budget | Bill rate ← Role on project's active **Rate Card Version** (falls back to card default); if Rate Cards activated, **per-project rate edits are disabled**. Cost ← account-member cost rate, per-project overridable. |
| **Harvest** | user/client/project/task | 3-state `unsubmitted/submitted/approved`; weekly lock; only Admins withdraw; **gated to Enterprise tier** | Per-entry boolean, `budgeted` flag for budget consumption | **Mode per project** (`bill_by` = Project / Tasks / People), with **project-specific override of the account default** within that mode. Rate snapshotted onto entry (`billable_rate`, `cost_rate`). |
| **Forecast** | No time entries — actuals live in Harvest | N/A | N/A | N/A |
| **Float** | Project(**required**)+phase/task optional; pre-filled from schedule but stays independent | **None** — no submit/approve step documented | Inherited from project/phase/task, never entered per-entry | True chain: person default → project override → **phase override**. Separate cost rate (role/person) vs bill rate (role/person/project/phase); client rate cards, Pro-tier |
| **Runn** | "Actuals" → person/project/**phase** (auto-filled), NB toggle | **None — stated outright**; workaround = lock + a Timesheet Note | NB toggle per entry | **Role-based only**: rate lives on the role, not the person; Rate Cards (Standard/Internal $0/Custom) reusable across projects; project-specific override > project's card > role default. Rate changes don't retro-apply to existing projects. |

## 3. Planning views & resource management

| Product | Views | Allocation/assignment/actual split | Critical path | Capacity/utilization |
|---|---|---|---|---|
| **Odoo** | Kanban/List/Calendar/Gantt/Graph/Pivot (**Gantt is Enterprise-only**); separate **Planning** app for shifts | Planning **shift** (forecast) vs Timesheet (actual); progress bar reconciles when both exist on a task | None documented | Per-employee billable-hours target vs actual ("Billing Rate Indicators"); no team-level capacity report in Project itself |
| **ERPNext** | Gantt, Kanban (by Status), Calendar, List, Report | **None** — no allocation/booking object in Projects | Not documented | Only a retrospective Project Profitability Report (billed hours ÷ working days) |
| **BC Jobs** | **List-only in the client**; Gantt exists only as a **Power BI report** (GA 2025 wave 1) | Allocation = just creating a planning line for a resource; no booking object | **Confirmed absent** | Resource Capacity page (matrix + templates); Resource Utilization report is retrospective only |
| **D365 Project Operations** | Board + Gantt/Timeline (Project for the Web), task checklists (≤20 items), multi-level undo | **Bookings** (project-level, hard=capacity-consuming/soft=tentative) vs **Assignments** (task-level) — **not kept in sync**; Reconciliation view shows drift | `msdyn_iscritical` field exists; user-facing critical-path viz **not documented** | Target billable utilization on role/resource; formula = chargeable hours ÷ (work hours − out-of-office − non-working days); **only approved, chargeable time counts** |
| **SAP B1** | Gantt (**report only**, no editing/dependencies), Detailed Project Overview tree | **None** — resources only enter via production/work orders | None | **None** — no capacity/allocation/utilization construct |
| **NetSuite native PM** | Schedule subtab: Planning/Tracking/Variance; Gantt with zoom, milestones, progress bars | 3-layer, explicit: **Allocation** (project-level pool) → **Planned Work** (adds a distinct field) → **Actual** | **Yes** — documented, calculated automatically | 3 utilization flavours matching the 3 layers: Allocated/Planned/Actual, over work-calendar-hours × target utilization |
| **SuiteProjects Pro** | Outline/Gantt/Task Detail views, simultaneously displayable | **Advanced Booking Worksheet** (Resource Planner feature + Support-enabled): green/yellow/red utilization heatmap, up to 2,000 bookings shown | Not documented | Booking worksheet is the utilization surface; dedicated topic on reconciling time entries vs bookings vs worked hours |
| **Workday PSA** | Not public (no Gantt/kanban/critical-path claims made) | "demand" (open roles) vs assigned workers — allocation/assignment split implied | Not public | "utilization trends," scenario modelling by toggling projects on/off — marketing only |
| **Scoro** | Gantt (drag dependency lines, zoom, "zoom to fit"); Kanban + **Task matrix** (2-axis); List | **Bookings** (Tentative/Fixed, capacity heatmap) explicitly separate from Tasks: "bookings help you plan people, tasks help you plan work" | Not confirmed | Utilization report reconciles Bookings layer (forecast) vs Tasks&Time layer (actual) vs unscheduled planned hours |
| **Productive.io** | List/Table/Board/Gantt/Timeline/Calendar; Gantt & Board are Professional+ | **Bookings** (Hours/day, %, or Total; Confirmed default, toggle Tentative) vs task assignment; report separates "Workload" from "Scheduled" | Not confirmed | Capacity − time off = Available; Utilization = worked ÷ **available** (not raw capacity) — deliberately excludes time off from the denominator |
| **Teamwork.com** | Gantt/Board/Table/List/Calendar/Timeline/Portfolio board | **Two separate tools**: task-driven **Workload Planner** (capacity vs estimated task time) vs allocation-driven **Scheduler** (works before tasks exist; billable allocations feed profitability before any task/log) | **Yes**, gated feature ("Show Critical Path") | Capacity = working hours − unavailable time; compares vs Logged vs Allocations; default utilization target 80% |
| **Kantata** | Global/Local/all-project Gantt, Boards (kanban+agile) | **4-tier funnel**: Estimate → **Allocation** (project-level) → **Assignment** (task-level, `allocated_minutes`) → Time Entry (actual); hard vs soft allocations (soft-only for placeholders) | Yes, via dependency "Critical Path" button (KB) | 7-tab Staffing & Capacity dashboard (heatmaps, availability, role availability, capacity scenarios); skills-based "Recommendations" matching engine |
| **Harvest** | None (no scheduling UI) | N/A | N/A | Account default hours/week + per-person override; **not enforced**, feeds only the Team report |
| **Forecast** | Schedule > Projects / Schedule > Team, Day/Week/Month zoom | Tentative expressed by **who** holds it (a placeholder = yellow), not a per-assignment flag | None | Capacity vs Availability views; heat-map green/red/black/grey; Time Off is an undeletable special project |
| **Float** | Schedule (person-centric) + Project plan (project-centric) | 3 distinct concepts: Scheduled hours / Logged time / tentative-draft status; **two separate "unknown person" mechanisms** — Unassigned Role (demand, transfers on fill) vs Placeholder (hiring/overflow/non-human) | None; only "linked allocations" | Capacity = work hours + planned work + time off; Utilization = scheduled ÷ capacity; % allocation excludes public holidays/full-day leave from the 100% base |
| **Runn** | Project Planner (rows=projects) / People Planner (rows=people, incl. Placeholder Demand FTE view) | Tentative/Confirmed at **project** level; **saved scenarios** (what-if) unique to Runn; Placeholders wired into a full Resource-Request workflow with skills matching | None; only the one-phase-per-day rule | Utilization = hours ÷ "Total Effective Capacity" (composition not fully documented); target-utilization bands (Advanced plan) |

## 6. Tier gating and build-order signal

- **Odoo**: Community = core Project + basic timesheets + SO↔project billing; **Enterprise = Gantt, timesheet grid/timer/validation, Planning, Field Service, Documents**. Module dependency graph shows the order: `project` → `hr_timesheet` (cost only) → `sale_project`/`sale_timesheet` (both `auto_install`, i.e. billing was bolted on) → `planning` → `industry_fsm`. **As of 19.2, Field Service was discontinued and folded into Planning** — Odoo concluded dispatch belongs with resource scheduling, not the task model.
- **ERPNext**: fully open-source, GPLv3, **no feature gating at all** — tiering is hosting/support only. A credible v1 needs only ~6 doctypes (Project, Task, Timesheet, Activity Type, Activity Cost, Project Template, Project Update).
- **BC**: Jobs/Resources/Time Sheets are in the base **Essentials** tier (Premium = Manufacturing + Service Management only). Renamed Jobs→"Projects" in 2023 wave 2 (captions only, tables still named `Job`). Shipped stages/tasks/subprojects as the MVP, added Gantt/billing-wizard one release later, then **nothing substantive for ~7 years** until Power BI Gantt in 2025.
- **D365 Project Operations**: succeeded **two** products (PSA + Finance's Project Management and Accounting). Explicit trade: bought a scheduling engine (Project for the Web) instead of building one, and **lost project templates** in the process. Revenue recognition/full expense/customer invoicing are **ERP-integrated deployment only**, not Core.
- **SAP B1**: single checkbox, no SKU — **base feature**. Rollout: core stages/tasks/subprojects shipped in 9.2 (2015); Gantt+Overview+Billing Wizard added one release later (9.3, 2017); essentially unchanged since.
- **NetSuite**: explicit free→paid ladder — **Basic Projects (free)** → **Project Management add-on** (schedule/resources) → **Job Costing & Budgeting add-on** → **Resource Allocations add-on** → **Charge-Based Billing** (needs Advanced Billing too). SuiteProjects Pro (ex-OpenAir) was acquired in 2008 and run as a separate product for ~17 years specifically because the native module couldn't do PSA-grade resourcing/rate-cards/utilization — rebranded 2024-25.
- **Workday PSA**: sold as separately-licensed, *adjacent* products (HCM, Project & Resource Management, Project Financials, Services CPQ) whose whole pitch is "single source of truth," not feature tiers.
- **Scoro**: two overlapping pricing generations; new modular model sells apps à la carte (Do/Deliver/Track/Resource/Sell/Estimate/Spend/Invoice). Kanban/basic time-billing in the lowest tier; **Gantt, Timesheet, Bookings, Utilization mid-tier; WIP report and full Customer Portal top-tier only**.
- **Productive.io**: notably **puts resource-planning/Bookings in its entry Essential tier** (unusual — most competitors gate this); Gantt, revenue recognition, timesheet locking, and Scenario Builder are gated higher.
- **Teamwork.com**: Free/Basics has tasks+time tracking but **no resource scheduler, no financial budgets, no profitability**; Accelerate adds Scheduler+time retainers+critical path; **Optimize is where profitability/financial-budgets/cost data first appear**. Founded 2007 shipping PM+time-tracking+milestones+files simultaneously — not sequentially.
- **Kantata**: no public self-serve pricing at all (contact-sales only). History: core PM+time-tracking first (Mavenlink, ~2008-10 per 3rd-party sources), then an explicit **2017 "first end-to-end resource management" launch** (4-phase: Estimate/Plan/Execute/Analyze), then the 2021-22 Kimble merger creating Kantata (adding Talent Network, Delivery Analyzer, RightResource).
- **Harvest/Forecast/Float/Runn**: consistently **per-seat pricing with the planning seat as the billing unit**; **time tracking approval + profitability are Harvest's Enterprise-only differentiator** (inverted from the PSA norm — Harvest's free tier is time tracking, approval is the upsell); Float/Runn instead gate **time tracking itself** one tier above pure scheduling (Float Pro, Runn Standard).

## 7. Synthesis

**(a) The common core every product has.** A Project container; a Task (or task-equivalent) that can optionally be billable; some notion of assignee(s), start/due dates, and status; a time-entry record that references at minimum a project (task is often optional — Harvest and Scoro are the outliers requiring a task); a billable flag on that time entry; a rate that resolves from *somewhere* (person, role, or project) at the moment of entry or invoicing; a way to turn accumulated time/fixed amounts into an invoice; and some form of budget number to compare actuals against. Every vendor also separates **cost rate** from **bill rate** as two independent numbers, even the simplest ones (SAP B1, Harvest).

**(b) The two-to-three dominant task/milestone data models, and their trade-offs.**
1. **Self-referential task tree with milestone-as-flag** (ERPNext, NetSuite native, Kantata's `story_type`). Cheapest schema — one table, arbitrary depth, milestones get every task field for free. Trade-off: milestones end up either meaningless (ERPNext: no documented effect) or entangled with work-item semantics unless deliberately decoupled from billing (Kantata's separate Billing Milestone object is the fix).
2. **Fixed-depth hierarchy with a real Phase entity** (Odoo, Scoro, Float, Runn, SuiteProjects Pro, D365 PO's summary/leaf WBS). Better for resource planning (a phase is a natural allocation bucket, and Runn's one-phase-per-person-per-day rule shows how load-bearing this can be) and for phase-level rate overrides (Float). Trade-off: more objects to keep consistent (Runn explicitly does *not* sync phase dates to child assignments — a documented modelling trap).
3. **List/ledger model with no tree at all, dates borrowed from a discipline that isn't scheduling** (SAP B1's stage rows with money-weighted Contribution%, BC's indented Job Task list with Begin/End-Total groupings copied from the chart of accounts). Cheapest to build and to reconcile with GL postings, but dead-ends on any credible planning UI — both vendors' own roadmaps prove it (SAP added nothing after 2017; BC didn't get a Gantt until 2025, and even then only as a Power BI report, not in the client).
Milestones-as-billing-object (Project Operations' Contract Line Milestone, Kantata's Billing Milestone) is the one pattern that recurs specifically where a vendor needed milestones to *drive money*: in both cases the task-level milestone link is decorative and the invoicing milestone is a separate row on the sales/contract side.

**(c) How time/billing attaches to the hierarchy.** Two families: (1) **the time entry resolves its own rate at entry time and gets a snapshot** (Odoo, Harvest, Kantata, Float partially) — simplest, historically correct, but requires the resolution logic to run per-entry. (2) **the time entry is a raw fact and rate/billability is resolved downstream at invoice time** (BC's planning-line/Usage-Link model, Productive's recognized-vs-billable split, D365 PO's editable invoice-line billing type) — more flexible for write-offs and PM discretion, at the cost of a reconciliation step. Every vendor that publishes an explicit rate-precedence *chain* (Teamwork, D365 PO) rather than a *mode switch* (Harvest, SuiteProjects Pro, Scoro, Runn) does so because they support multiple simultaneous billing arrangements per account; a mode switch is adequate only if a tenant is expected to pick one rate philosophy account-wide. Approval is close to universal in the heavier PSA/ERP tools and consistently modeled as a state machine (Draft/Unsubmitted → Submitted → Approved/Rejected, sometimes with Recall) that **locks the entry and often only creates the financial "actual" on approval** (explicit in D365 PO and Productive) — but is conspicuously **absent** in every lightweight scheduling tool (Float, Runn) and gated to the top tier where it does exist in a "PM-lite" tool (Harvest Enterprise).

**(d) What the best-regarded planning products do differently.** Float, Runn, Kantata, Scoro, Teamwork and D365 Project Operations all independently arrived at the **same three-layer separation**: a forward-looking *allocation* (person-to-project, hours or %, tentative/soft or confirmed/hard), a more granular forward-looking *assignment* (person-to-task, sometimes with its own effort-driven scheduling math), and a backward-looking *actual* (the time entry) — with **utilization reports computed in exactly those layers** (NetSuite explicitly has Allocated/Planned/Actual Utilization; Runn plots Scheduled/Actual/Projected/Budget on one chart). None of these tools lets the actual silently overwrite or auto-reconcile the plan — the point of the split is to make drift visible (D365 PO's "Reconciliation" view; Runn's "Variance" tab flagging missing timesheets). The other recurring differentiator is a clean **two-object placeholder model**: Float alone splits "unassigned role" (demand you'll fill from existing staff, transfers cleanly on assignment) from "placeholder" (a hiring/overflow/non-human slot); Kantata pairs this with a skills-matching "Recommendations" API. Products without this split (BC, SAP B1, ERPNext, Workday-public-docs) simply have no credible resource-planning story at all.

**(e) Suggested build order for Vantigo, and why.** Vantigo already has a Project entity (codes, roles, billing type, budget, billing lines pinned to product variants) and Time Tracking is next. Given the evidence above:
1. **Task + minimal WBS now, alongside Time Tracking.** Use a self-referential task table (ERPNext/Kantata pattern) rather than a fixed-depth phase hierarchy — cheapest schema, defers the phase-vs-no-phase decision, and Vantigo's project codes (KVEM1000) already give a natural top-level grouping. Give the time entry a required Project reference and an *optional* Task reference (Teamwork/Kantata pattern, not Scoro/Harvest's task-required pattern), plus a billable flag and a work-type/activity dimension — this is what makes rate resolution and T&M invoicing deterministic later (NetSuite's lesson: "billable ⇒ rate-bearing reference required").
2. **Rate resolution as an explicit, documented precedence chain from day one** (Teamwork's model: task/project override → role → person default; cost always from the person, snapshotted onto the entry like Harvest/Kantata do) — retrofitting this after data exists is exactly what NetSuite/Runn's "changes don't retroactively apply" caveats warn against.
3. **Billing-milestones as a distinct object from delivery-milestones, attached to the billing line / contract, not the task** — directly informed by Odoo, D365 PO and Kantata all converging on this same separation once they needed milestones to drive money. Since Vantigo already models billing lines pinned to product variants (KVEM1000-PM), a milestone can simply be a billing-line row with a target date and a %/amount, independent of whether a task-level milestone flag ever exists.
4. **Approval workflow as a first-class state machine on time entries** (Draft/Submitted/Approved, actuals recognized on approval) before building invoicing off timesheets — every serious PSA product treats this as foundational, not an add-on, and it is cheap to build early and expensive to retrofit once invoices already reference raw entries.
5. **Simple budget-vs-actual (hours and cost/revenue) per project/billing-line next**, modeled as Odoo's Expected→To-Invoice→Invoiced three-column pattern or Scoro's Quoted-vs-Actual table — this is achievable with the data already captured by steps 1–4 and is table stakes before any planning UI matters.
6. **Resource allocation/planning last, and only as a genuinely separate object from tasks** (an Allocation table: person × project/phase × date-range × hours-or-%, tentative/confirmed) — not bolted onto the task table. This is the single most consistent lesson across the whole survey (§d): every product with a good planning reputation treats allocation, assignment and actual as three distinct tables, and the ones that don't (BC, SAP B1) have visibly stalled planning UX for a decade-plus. Defer Gantt/critical-path (rare, and even NetSuite's is the only convincingly "real" one) and defer WIP/earned-value accounting (only BC has a fully worked, published model, and it's the most complex thing in this entire survey) until there is a proven need — they are the features every vendor visibly shipped last.
