# Staff phase 1, delivery A1 — People and employments: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Steps use checkbox (`- [ ]`) syntax for tracking. A pre-flight review of this plan precedes Task 1.

**Goal:** A new `staff` module in which HR keeps the company's people — identity, contact, next of kin, bank, the sealed national id — their employments as Norwegian arbeidsforhold with dated terms carrying the a-melding and § 14-6 fields, the company's structure, and a history of every change; with its own app (People, the person page, Settings, My page), registered everywhere a module is, and documented.

**Architecture:** A standalone module in the Expenses mould: directory `apps/server/internal/staff` (package `staff`), schema `staff`, URL `/api/v1/staff`, contract `openapi/staff.yaml`, frontend package `apps/staff/frontend` (`@vantigo/staff-ui`). It depends on identity only — `Deps.Users` for names and the user picker, nothing else — and reads no other module. One migration for this delivery, `000NN_staff_foundation.sql`, with every column of `staff.people` and `staff.settings` the spec's §3 names (later deliveries add tables and their own columns, never these two tables' columns), plus the A1 tables. The sealed identifiers use a new `secrets.Box.MAC`. Documents, import and export, the payroll CSV, retention, stats and attention (A2), absence (B) and the accounts worker (C) are NOT in this plan — but the schema and the contract must not paint them into a corner.

**Tech stack:** Go (pgx v5, sqlc, goose, oapi-codegen strict server), PostgreSQL, React 19, Mantine, TanStack Router + Query, Vitest, Bun.

**Spec:** `docs/superpowers/specs/2026-10-11-staff-foundation-design.md` (revision 2, `044a32f3`) — delivery A1: §1, §2 S1–S7, S17, S21, S28, S29; §3.1–3.4, 3.6 (events, settings; links per reading 1); §4 (Days and the zone, Terms, Managers, Sealed fields, Locking); §5; §6 (Meta, People, Employments, Structure, Settings except absence and accounts fields, Me); §7 (My page's profile, People, the Person page's Profile, Employments and History tabs, Settings' structure and A1 fields, Host); §8.2, 8.5, 8.6, 8.7; §9 (the A1 items); §10 (the A1 items); §11. Research: `docs/superpowers/research/2026-10-11-staff-module.md` §4.1, §4.7, §4.9, §7.

### Task 1: The platform's MAC, and the identifier package (S4; pure, parallel with Task 2)

`secrets.Box.MAC(purpose string, data []byte) []byte` — HMAC-SHA256 under `keyFor(purpose)` (the same HKDF derivation as `Seal`; a distinct purpose string gives a distinct key, so a MAC key never equals a sealing key); constant-time compare helper `secrets.MACEqual`; `Format`/`LogValue` unchanged (they never print keys). `internal/staff/ident` is a stdlib-only leaf: `ParseNationalID(kind, country, raw) (Normalised, error)` — fødselsnummer and d-nummer: 11 digits, the d-nummer's first digit raised by 4, both control digits (weights `3 7 6 1 8 9 4 5 2` and `5 4 3 2 7 6 5 4 3 2`), the synthetic test ranges accepted (month + 40, month + 80; spec reading 24), a date that exists; foreign: 1–40 chars `[A-Za-z0-9-]` with an alpha-2 country, upper-cased; `IndexInput(n) []byte` — `kind | country | normalised`, the domain-separated MAC input; `ValidateBankAccount(kind, raw)` — BBAN 11 digits MOD11 (weights `5 4 3 2 7 6 5 4 3 2`), IBAN mod-97 with the country's length table for NO/SE/DK/FI/DE/GB/NL/PL/… (a table, extendable; unknown country → length 15–34 and mod-97 only); `Last4`; `ValidateOrgNumber` (9 digits MOD11, weights `3 2 7 6 5 4 3 2`).

- [ ] **Failing tests first**: MAC deterministic per purpose, different across purposes, 32 bytes, `MACEqual`; `Format`/`LogValue` still redact; fødselsnummer table (valid, each control digit wrong, impossible date, d-nummer, both synthetic ranges, foreign normalisation, country required); `IndexInput` differs for the same digits under two kinds; BBAN MOD11 (valid, wrong, the "10" remainder case refused); IBAN (NO, DE, GB valid; wrong check; wrong length); org number; purity test (no non-stdlib import).
- [ ] Implement; gates (`internal/secrets`, `internal/staff/ident`, vet, lint, race).
- [ ] **Commit** `feat(platform): a keyed MAC on the secrets box, and the identifier checks Staff needs` — docs: `en/contributing/platform-packages.md` (new, English only; `sources: apps/server/internal/secrets, apps/server/internal/staff/ident` — `internal/calendar` joins it in delivery B) with the MAC, the purposes convention and the rotation rule; `en+nb admin/installation.md` gains the `APP_SECRET` rotation note (the national-id index); `contributing/index.md` lists the page.

## Readings of the spec

Each is a choice the spec leaves open, or a place where two of its passages cannot both be built, decided here for the user's verdict; the first is a spec amendment the pre-flight should confirm.

1. **`identity_links` lands in A1, with a manual link.** The spec's §1 puts the table in delivery C's migration, but §5's "Self" and "Manager" audiences, `/me` and the People list's "linked user" all need the person ↔ user relation from the first delivery. A1 creates the table as §3.6 defines it and lets `staff:manage` link a person to an existing user by hand (`PUT /people/{id}/account { userId }`), through `Deps.Users` read outside the transaction; C adds the flag's behaviour, the worker and identity's managed users, and turns the manual link into one of several ways a link appears. The spec's §1 (A1, C) and §3.6 should be amended to say so.
2. **The settings contract grows with the deliveries**: A1's `PUT /settings` accepts only the five A1 fields; the absence, account and retention columns exist from A1's migration (the spec's "every column") but reach the contract with B, C and A2, so no delivery adds a column to `settings` or `people`.
3. **The employee number is generated as `prefix + next` without padding**, so `EMP` and 7 give `EMP7`; a company wanting `EMP007` sets `next` to 7 and the prefix to `EMP00` for as long as that lasts — padding is a later setting if asked for.
4. **`display_name` is derived once** at creation from given and family name and then independent (a nickname, a double surname), editable by HR and by the person on `/me`.
5. **`DELETE /people/{id}` is a hard delete of a person created in error** — no employment, no link, no absence (B), no document (A2) — recorded as an installation-level event; anything else is `person_in_use`, and the retention run (A2) is the only other way a person's data leaves.
6. **The person's private group is editable by HR too**, not only through `/me`: HR types the address a new hire gives; the matrix's ✎ for `staff:manage` on the private group is read that way.
7. **A manager's visibility in A1 shows the work group and the employment summary of their reports**; the absence and case columns of the matrix wait for B. The audience is resolved from the terms in force **today**, so a manager-to-be sees nothing until their first day.
8. **`pay_components` comparison for `salaryChangedAt`** sorts by name and compares name and amount only; currency and period changes do not move the date. The spec says "name and amount"; the plan makes the sort explicit.
9. **The contract check's document items** (a signed contract, a-item "partenes identitet" is always present once a person and a business unit exist) answer `present: false, source: "document"` in A1 and flip when A2's documents land; the check is informative, never blocking.
10. **`GET /users/search` is a Staff endpoint** wrapping `Deps.Users.SearchUsers` for the link picker, capped at 20, `staff:manage`, so the Staff app needs no identity UI code — customers' assignable-users endpoint is the precedent.
11. **The event payload's shaping is by class list** (`payload_classes`), not by parsing the payload: a `person_updated` event carrying a D field is shown to a `staff:view` caller as `{fields: {street: "changed"}}`, which is the spec's rule made mechanical.
12. **The mail on a bank-account change goes to the private email when set**, else the work email, and is skipped with a logged line when the person has neither; the spec says "mails the person".
13. **`PUT /people/{id}` is a full replace of the editable groups the caller holds**, under `If-Match`; fields of a group the caller may not write are refused on the field (`field_not_writable`), never silently kept — one more refusal code than the spec lists.
14. **The structure's `is_default` is exactly one per table and the first row becomes it**; the spec names the column without the rule.
15. **The migration number is decided when Task 2 lands**, not in this plan (`00042` today), because the invoices phase 4 PR 2 branch may land first.
