## Readings this plan takes (each goes into D §13 as amendments 23–36 by Task 5a)

23. **The gap statuses are S13's six**, judged in this order on the person's current row of the item's competence: no current row → `missing`; a declared certificate → `declared_only`; `minLevel` set and the row's level below it → `below_level` (a row without a level is never below); `mustBeValid` and the row not valid today (`validTo` passed → `expired`; `validFrom` not yet reached → `missing`); `mustBeValid` and `validTo` within the competence's `reminderLeadDays` → `expiring`; otherwise `met`. Every item carries `declared` (the row is unverified — a skill declared counts as met, with the flag, N3.16) and `archived` (the competence is archived, §9: the item stays and is reported). **Not met** is every status but `met` and `expiring`; the gap count on the item and on the response is the items not met, an archived competence's included.
24. **`mustBeValid: false` means the validity is not judged**: an expired or not-yet-valid row is `met` (or `below_level`, or `declared_only` for a certificate); `expiring` is never answered for such an item. A `mustBeValid` item on a competence without validity is accepted and judged as `met` whenever a row is held (D §6).
25. **A profile reaches a person two ways, and the list says which**: each row of `GET /people/{id}/competence-profiles` and each profile of the gap list carries `assigned` (a `person_profiles` row) and `department` (the `StaffDepartmentSummary` of the department whose default it is) — one row when both. The **department** is the one named by the terms in force today of the person's place — the earliest employment in force today, by start then id, as `rulePlaces` judges a group rule — none when no employment is in force (§9: only assigned profiles apply).
26. **An archived profile reaches nobody**: it is listed on the person with `archived: true` so HR sees the assignment, but raises no gap and no item, and a department whose default it is has no default while it stays archived. Assigning an archived or unknown profile is a plain field error on `profileIds[i]`, while an assignment kept from before is never re-judged; a department PUT naming an unknown profile, or an archived one that is not already its default, is a plain field error on `competenceProfileId` — a department keeps its own archived default (as it keeps an archived parent), which stays without effect. No new refusal code (as amendment 22).
27. **A profile's `key` never changes** (as a competence's, amendment 2): the change request carries `names`, `archived` and `items`; the items are replaced whole under the profile's `If-Match`. The catalogue writes the installation events `competence_profile_created` and `competence_profile_updated` with `competenceProfileId` and `fields` — `key`, `names`, `archived` and `items` as the list of `{competenceId, minLevel, mustBeValid}` in catalogue order, before and after, each field only when set or changed — as `competence_created`/`competence_updated` are written; a change that alters nothing bumps the revision and records no event.
28. **A profile's items**: at most **50**; a duplicate `competenceId` is a plain field error on the later index (`items[i].competenceId`); an unknown, hidden or archived competence on a **new or changed** item is `competence_unavailable` on `items[i].competenceId` (as a new row's or interest's), while an unchanged item naming a competence archived since is kept (§4: it stays; amendment 18's rule); `minLevel` 0–4 is allowed only on a competence with a level, else `level_not_allowed` on `items[i].minLevel` (D §6); `mustBeValid` left out is true. A profile item with a `minLevel` counts as the competence being **in use** for `competence_in_use` (changing `hasLevel` on a company competence), so no item's level is orphaned.
29. **The matrix** (`GET /competence-matrix`, `staff:view` or `staff:manage`, the uniform 403 otherwise) lists every person **active today** and not erased (as the contract does), ordered by name, each with the current rows **valid on `validOn`** (default today in the business zone) of the competences selected — all of them, or `categoryId`'s, or the `competenceId`s given (repeatable, as D S14) — as `{competenceId, level, verified, validFrom, validTo}`; a row not valid on the date is absent, not shown as expired (the gap list says that). `verifiedOnly` drops declared rows; without it a declared certificate is shown with the badge (reading 11), since only the filter treats it as not held (S3). `minLevel` drops rows of a competence with a level below it and leaves a competence without one untouched. With `competenceId`s given, a person is listed only when, after those judgements, they hold every one; otherwise every active person is listed, with no rows when they hold nothing selected — the matrix is the directory with competences. The response carries as columns (`competences`, summaries, catalogue order) the `competenceId`s given, or, when none is given, the competences of the cells shown — so a filterless matrix shows what is held, not the whole catalogue — and the people as rows (`personId`, `name`, `competences`). `categoryId` and `competenceId`s together intersect: the columns are the ids given, and one outside the category has no rows. A `minLevel` outside 0–4 or an unknown `competenceId` is a plain field error (400) keyed by its name; a malformed `validOn`, `minLevel` or `competenceId` is the decoder's bare 400, as every date query parameter's; an unknown `categoryId` answers no columns.
30. **The interests overview** (`GET /competence-interests`, `staff:manage` alone — never the Approver, amendment 16; the uniform 403 otherwise) groups every interest of an **active, not erased** person by competence, in catalogue order, competences with at least one interest only (archived or hidden ones included when an interest names them, since every existing row is kept), each with `wantsToLearn` and `wantsMore` as `StaffPersonSummary` lists by name — `held` decides the bucket as `ListPersonInterests` does.
31. **The `competenceGap` item**: one per person, `id` `competenceGap/<person id>`, `count` the items not met across the person's unarchived profiles (reading 23), `occurredAt` today in the business zone (a gap has no day of its own; it is computed on read), `title` the person's name; to `staff:manage` for everyone and to a manager for their reports today, never `staff:approve` alone, never one's own; only people active today and not erased. It is read — the assignments, the departments' defaults, then the profiles, their items and the current rows of the people concerned, short-circuiting when nothing reaches anyone — only when `c.Manage || len(reports) > 0`, so the Approver's and the linked nobody's statement counts stand.
32. **The field group "Profiles and gaps"** is `groupProfiles` ("profiles"), read by Self, Manager, Approver, `staff:manage` and `staff:personal-data` (D §5's row), never the colleague: `GET /people/{id}/competence-profiles` and `GET /people/{id}/competence-gaps` answer the bare 404 outside it. `PUT /people/{id}/competence-profiles` is `staff:manage`'s: 403 to anyone else who sees the person, 404 to one who does not. The capability block gains `canAssignProfiles` (`a.Manage`), so the apps carry no audience logic.
33. **`profileAssignments` is in both exports**, filled for an audience that reads the Profiles group — the person's own included, since the tab shows them their profiles — and an empty list, never absent, to anyone else; S17's "HR's gains" is read as the complete export gaining it too, under the same rule as the four wish sections.
34. **`profiles_assigned`** is recorded on the person when the set changes, payload `{"fields": {"profiles": {"from": [keys], "to": [keys]}}}` (an empty side left out, as every `fieldChange`) — the sorted profile **keys**, catalogue words, not the person's (amendment 21 keeps values out of the wish payloads; a profile key names a position, not a wish); the field is class D (`rows`: `person_profiles.profile_id`). The actor is HR.
35. **The departments' default is a full-replace field**: `StaffDepartmentRequest.competenceProfileId` left out clears it, as `managerPersonId` left out clears the manager; the response carries `competenceProfileId` when set. The department PUT records no event, as today.
36. **The profiles catalogue is readable by anyone with `staff:access`** (as the competence catalogue is, amendment 1: it holds no personal data), every profile listed, archived included with `archivedAt`, so Settings restores one; writes are `staff:manage`'s. **No `PreferenceFit` method** is added to `contracts.Workforce`: its shape — `PreferenceFit(ctx, personID, Booking) (Fit, error)`, `Booking{From, To; Weekdays; Parts; LocationID; HoursPerWeek; ConsecutiveDays; Travel; Remote}`, `Fit{Score 0–100; Lowered []kind}` — and its rule (start at 100; each preference the booking contradicts lowers it by its weight × 10, the kind named, never the value; the availability declaration is Staffing's to enforce, S10) are written into the reference's Workforce contract section as the matching contract's Staff side, to be added to the interface with Staffing's first delivery (S15).
