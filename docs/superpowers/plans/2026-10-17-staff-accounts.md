## The owner's answers (2026-10-17)

1. **The account's email** changes with the person's record **only while the user is pending** (no credential). Afterwards a difference raises `accountEmailDiffers` (staff:manage) and an Owner changes the address in identity. Name, language and employee number still sync. (B3.)
2. ***Disable now* also turns the flag off**, in one action, so the worker leaves the account disabled until HR turns the flag on again. (I3.)
3. **Approval mails to holders by right are a fallback**: a request mails the person's manager-deciders as in B; the active holders of `staff:approve` and `staff:manage` (Owners by the wildcard included) are mailed only when the person has **no manager-decider with an active user**. The inbox and `absenceAwaitingDecision` are unchanged. An HR-only request mails the other active holders of `staff:personal-data`, neutrally, as its only deciders (reading 20).
4. **A permission's holders** are resolved through direct roles, roles mapped to an access group the user belongs to, and the Owner role; a delegation grants authorization management only (`id/access.go:247-263`), so a delegate holds K only if one of those gives it. (I12.)
5. **(after Task 1a's review) The roles Staff may give never grant administration**: a custom role carrying `identity:manage` (identity's non-delegable keys), `staff:manage`, `staff:personal-data` or `staff:approve` is refused from the set, and a role in the set cannot gain such a key by an edit — taken as built.
6. **The open questions answered** (2026-10-17): B's narrowed self-approval stays narrowed; HR's residual reach over Staff-managed users is accepted; adoption is the Owner's in identity alone; the authority mode stays derived and recorded, **the Entra module revisits it in detail** (a setting beside the derived mode).
7. **B's open questions 11–13 become settings, in C (Task 5b):** the `ammefri` seed is paid (aml. § 12-8 (2): pay for up to one hour a day in the child's first year on a working day of seven hours or more), and HR may set `paid` on any seeded type, so a company paying beyond the law says so; an installation setting erases pregnancy and health-appointment rows on the health schedule (off by default, as built); an installation setting erases a sick-leave case's dates and milestones fully in the health erase (off by default, as built).

- **The lock rule, strict.** No directory, accounts, mail or object-store call inside any transaction or read-only snapshot, in Staff (the recorder fails the test) or in the worker. The worker claims a link in one short transaction on the pool and **commits**; reads the person's facts in a snapshot and closes it; calls identity holding no connection, under a 2-minute timeout; writes the result in a second short transaction that re-reads the person under its lock and checks the link's `lease_id`. No cycle-wide lock and no lease connection (B2; PR #124 is the counter-example). Identity's provider runs on identity's own pool in identity's own transactions and mails **after** its commit. Pool-of-one tests for the cycle, `POST /accounts/run`, *Disable now* and `GET /meta`.
- **The lock order (spec §4 Locking, extended):** the person `FOR NO KEY UPDATE`, then their employments, absences, cases, documents, **then their link**. The worker's claim takes the link row alone (`FOR UPDATE SKIP LOCKED`, its own transaction); the result write takes the person lock, then the link. Identity: the owner advisory lock (`ownerMutationLock`) for any change that can touch an Owner (adoption, unmanage, deactivate), as `setUserDisabled` takes it; then the invitation row, then the user row (accept).

## Readings of the spec

1. **Two migrations, `00050_identity_accounts.sql` and `00051_staff_accounts.sql`**, not one spanning both schemas: `TestNoModuleReferencesAnotherModulesSchema` (`srv/db/schema_test.go:133-152`) forbids it and `:210-232` ties identity's sqlc to `NNNNN_identity_*`. The spec's precedents (`00024`, `00040`) are one schema each; the multi-module precedent is 00037–00040's consecutive split. "One migration per delivery" (§1, reading 22) becomes one per schema for C.
2. **(owner's answer 4) A permission's holders** come from direct roles, group-mapped roles and the Owner role; a delegation grants none.
3. **"Active" for a holder** is not disabled, not pending, and not a SCIM-inactive non-Owner under SCIM — what a session needs (`sessions.sql:30`); a lockout is temporary and ignored. For the sole-holder rule this counts more holders, so it errs toward waiting.
4. **`AccountSpec` carries no `RoleIDs`**: identity assigns its own `provisioning_roles` (S26).
5. **Prepare assigns the built-in `User` role explicitly**: not every account has it (`users.go:280`, `invitations.go:325`, SCIM assigns none), against S25's "the built-in `User` role every account has".
6. **`account_managed`** is identity's 409 on deleting a Staff-managed user; `employee_number_taken` is reused in identity for adoption's collision.
7. **`identity_links.external_id` becomes nullable** (00042:271) so S27's `preparing` row needs no placeholder; `preparing` joins the link's states (no state check, by house style).
8. **(pre-flight B3) The self-service link and the managed link are one row**, and a Staff-managed user is reached only through `Prepare`'s number lookup: `PUT /people/{id}/user` refuses a Staff-managed user and a worker-state link (`link_managed`); the worker acts only when identity's employee number equals the person's. An unmanaged self-service link stays HR's, and the worker leaves it alone.
9. **A `preparing` link does not make a person "in use"**; the delete removes it, refused while leased.
10. **`account_email_kind` null reads `work`** (00042:106 has no default).
11. **Account events are the links group's** (Self, manage, personal-data), carrying codes and states only.
12. **The provider file is `id/provisioning.go`**: `id/account.go` already holds the signed-in user's own account (§8.3's `accounts.go`).
13. **The OIDC refusal is `account_locked`** (`oidc.go:98`), not `oidc_account_locked` (S23).
14. **Existing disabled users are backfilled `disabled_by = 'owner'`** and existing revoked invitations `revoked_reason = 'owner'`: before C only an Owner (or SCIM, whose `upstream_active` is separate) disabled or revoked.
15. **Adoption admits a SCIM-mapped user**: in federated mode the managed user *is* the IdP's.
16. **Accept's refusal for a named invitation is the uniform `invitation_invalid` 400**, telling an outsider nothing.
17. **`STAFF_ACCOUNTS_ENABLED` defaults on** like `STAFF_RETENTION_ENABLED`; nothing happens until HR turns a flag on and an Owner names the employee roles.
18. **Holder mails go to the identity address** (`Holder.Email`), the first Staff mail not to an address of its own register; B's reading 4 retired for holders by right.
19. **(pre-flight I6) The authority mode is recorded by the API process** in `system_settings`, so a worker-only process cannot disagree silently; spec S23's "derived from configuration" still holds for the API.
20. **An HR-only request is mailed, neutrally, to the other holders of `staff:personal-data`**, its only deciders (B reading 33), whatever the manager rule; no approve or manage holder is mailed for it.
21. **(pre-flight I8) Installation-level account items are derived from link rows**: the worker writes the reason on the links it would act on, so the API reads no worker memory and calls nothing at read time.
22. **`hrOnlySelfApproved` is read by every `staff:personal-data` holder**: at the time it is raised that is the self-approver alone (by definition), and a holder added later sees it while the absence lasts — the second pair of eyes the rule lacked.
23. **Two more settings columns** (`erase_pregnancy_health_types`, `erase_sick_case_dates`) are added in 00051, against 00042's "never to these two" comment, as B added `auto_carry_over_since`; and **a seed's `paid` becomes HR's to change**, `ammefri` excepted below the law's floor.
24. **(Task 1a review) `PUT /owner/provisioning-roles` takes no `If-Match`**, as identity's other `PUT`s; both writes are audited.
