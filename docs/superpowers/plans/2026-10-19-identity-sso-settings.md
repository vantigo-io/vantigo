# Entra phase 1, delivery A — the SSO and SCIM settings into the database: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Tasks 3, 4 and 7 get a security-focused reviewer (they move credentials and change what a session is resolved under). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the workforce OIDC provider and the SCIM credential move from the environment into one row, `identity.sso_settings`, that an Owner edits on a **Single sign-on** card under Workspace administration and that every reader — the session query, sign-in, the SCIM bearer check, the relying party, the status endpoints, the authority mode — reads through a 20-second in-process cache, so a change is in effect on every replica without a restart. The SCIM token is generated by the server and shown once; only its digest is kept. The client secret is sealed. An installation that still carries `OIDC_*` or `SCIM_*` imports them into the row once, at the first API start that finds the row never written, audits the names, and warns; afterwards the row wins and the variables are leftovers. The authority mode stops being a guard against a misconfigured worker, since the API and the workers now read the same row.

**Architecture:** `identity` only (`apps/server/internal/identity`, schema `identity`, `openapi/identity.yaml`, the host's Workspace administration page), plus `internal/config` (the loader keeps parsing the two blocks for the import and nothing else reads them). Branch `feat/identity-sso-settings`, cut from `research/entra-module` (the research and design, on `main` at `a529e1af`); the PR against `research/entra-module`, the stack's bottom. **One migration**, `00058_identity_sso_settings.sql` (00057 is the highest on main), with its pin test in `internal/db`. No new module, slot, permission or worker.

**Spec:** [`docs/superpowers/specs/2026-10-19-entra-design.md`](../specs/2026-10-19-entra-design.md) D1 and D2, its deliveries table (A), testing (A), readings 1 and 2; the research [`2026-10-19-entra-module.md`](../research/2026-10-19-entra-module.md) §1.1 (the whole reader surface, as a table) and §6.

**Pattern code:** `identity/system.go:28-62` (`maintenanceCache`: a mutex, the value, `fetchedAt`, `get(now, fetch)`, `evict()`); `identity/workspace.go` (an Owner's setting: validated before the transaction, the singleton row ensured and locked, audited before/after, the same value answering 200 with nothing written); `identity/authority_mode.go` (the mount-time record under `recordModeTimeout`); `identity/oidc.go:113-200` (`oidcRelyingParty`, `newOIDCRelyingParty`, the mutex-guarded discovery) and `:699` (`readClientAssertion`); `identity/scim.go:160-181` (`scimTokenValid`, `sameDigest`); `config/config.go:1248-1475` (the two loaders and their rules — moved, not rewritten); `invoices/credentials.go` (a sealed credential under its own purpose, never answered); `calendar/feed_tokens.go` (`newRSVPToken`'s shape for a generated token: 32 random bytes, `base64.RawURLEncoding`, SHA-256 at rest); `internal/db/schema_calendar_feed_test.go` (a migration's pin test); `identity/harness_test.go` (`withEnv`, `newHarness`) and `oidc_harness_test.go` (`withFakeOIDC`, `fakeOIDC.attach`); `apps/host/frontend/src/routes/workspace/-workspace-settings.tsx` and `api/workspace.ts` (the Workspace card and its API), `catalogs/admin.ts` (its strings).

`id/` is `apps/server/internal/identity/`, `mig/` `apps/server/internal/db/migrations/`, `A/` `docs/src/content/docs/{en,nb}/admin/`, `U/` `docs/src/content/docs/{en,nb}/user/`, `host/` `apps/host/frontend/src/`.

## Exact values

- `ssoSettingsCacheTTL = 20 * time.Second`; the token 32 random bytes; the previous
  token's overlap at most `24 * time.Hour`; the display name at most 100 characters;
  the secrets purpose `identity/oidc-client-secret`.
- Audit actions: `sso-settings.imported`, `sso-settings.changed`;
  `authority-mode.changed` unchanged.
- Problem codes: `oidc_links_exist` (409), `version_mismatch` (412), field errors on
  `provider`, `authority`, `clientId`, `clientSecret`, `workloadTokenFile`,
  `allowedDomains`, `displayName`, `previousExpiresAt`.

## Readings of the spec

1. The `GET` is `policy:Owner` and every write `policy:Owner+OwnerManagement`, the
   spelling every other `/owner/*` write uses; in code the two names are one check,
   Owner plus MFA while `OWNERS_REQUIRE_MFA` holds, so the `GET` needs MFA too. Only
   the PUT carries `If-Match`: the token issue and the deletes have no body to go stale.
   The six operations answer 429 like every rate-limited identity operation.
2. `GET /identity/providers` (the sign-in page's) reads the row, so the button appears
   within the TTL of a save; the SPA re-fetches it on the sign-in page's load as today.
3. The user directory and the provisioning provider each keep their own cache rather
   than share `Access`'s: both are built from `Deps` without an `Access`, and a 20 s
   lag between three caches in one process is within what D1 promises.
