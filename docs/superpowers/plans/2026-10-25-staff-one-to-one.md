# Staff phase 2, delivery B — the one-to-one: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Task 2 lands first, alone; 3a, 3b and 4 run in parallel against it, each owning its files; 5 after 3 and 4; 6 last. Nobody commits but the coordinator.

## Readings this plan takes (each goes into D §13 as amendments 16–22 by Task 5)

16. **The Seen set is the manager's and HR's, never the Approver's** (D §5's table: Approver "—" on Wishes; D S8 "the manager's Seen"). `canStampWishesSeen = (Manager ∨ Manage) ∧ ¬Self`; an Approver who is neither reads no wishes and stamps none. The capability block gains `canReadWishes` (D S18) **and** `canStampWishesSeen`, so the apps need no audience logic.
17. **The Seen stamp reaches `person_competences` too** (D §3.3 lists the two columns as B's): `POST /people/{id}/wishes/seen` stamps every row of the four wish tables and every **current** competence row with no stamp — a declaration the manager has read but not yet verified is thereby acknowledged. The stamp is exposed as `seenAt` on each row (the Competence detail group for a competence row), and the response counts what was stamped per table.
18. **A whole-list PUT is a diff, not a wipe**: rows equal to an existing one (interests by `competenceId`; preferences by `kind`, `value` and `weight`; declarations by every field) keep their row and its Seen stamp; a new or changed row is inserted unstamped; a row no longer sent is deleted. So "changed since" (D S8) is simply "not yet stamped". Catalogue availability (a hidden or archived competence, an archived location) is judged on new or changed rows only; an unchanged row is kept as it is (D §4 "keeps every existing one").
19. **No CHECK constraints** on the new tables, as 00042 and 00066 say: the module's validation owns D §3.6's rules and reports them per field.
20. **No person revision bump and no `If-Match` on the lists** (reading 15): the person is the only writer, and the lists are not under the person's revision.
21. **The event payloads carry counts and kinds, never values** (D S16): `interests_changed` the count before and after; `preferences_changed` the kinds added, changed or removed; `availability_changed` the count before and after; `wishes_seen` the rows stamped; `competence_reviewed` the review's date.
22. **No new refusal code**: a bad weekday, minute, date, weight or kind is a plain field error at its index; `competence_unavailable` is reused on `interests[i].competenceId`; a review dated after today is a plain error on `reviewedOn`; the review set reuses `own_record` for the person on their own.
