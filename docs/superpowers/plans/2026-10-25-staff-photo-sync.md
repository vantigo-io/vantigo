# Staff — the photo follows the account: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Task 2 lands first, alone; 3a (identity), 3b (entra), 3c (staff server) and 4 (the apps) run in parallel against it, each owning its files; 5 after 3 and 4; 6 last. Nobody commits but the coordinator.

**Goal:** HR's photo becomes the user's picture in Vantigo (a managed avatar that disables the user's own choice while it stands) and in Entra ID; when HR has set none, the user's own avatar is the picture, shown on the Staff page and pushed to Entra too; nothing flows back.

## Readings this plan takes (into D §8 as 8+ by Task 5)

8. **Identity judges the managed avatar as it judges an upload** (JPEG/PNG, 5 MiB, 4096 px) and answers `ErrAvatarInvalid`; Staff's bytes already pass, so the check guards the contract, not the flow.
9. **`photoSource` is `record` or `account`; the list row carries no source**, since the list has no avatars.
10. **The worker pushes the photo after the chain's main step, within the same claim**, and a photo failure is recorded as the link's failure (retried at the next poll) — not as its own link state.
11. **The My page menu calls identity directly** from the Staff frontend (same origin; the pattern Time uses for Projects), so Staff's API carries no proxy for the user's own avatar.
