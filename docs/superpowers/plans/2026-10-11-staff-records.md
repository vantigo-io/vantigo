# Staff phase 1, delivery A2 — Records: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Steps use checkbox (`- [ ]`) syntax for tracking. A pre-flight review of this plan precedes Task 1.

**Goal:** The records that make the register a personnel file and keep it lawful: a document archive per person with categories and retention classes; CSV import and export of the register; the payroll export behind a port; the person's own data exported; the retention run that erases per class and finishes; the dashboard's figures and attention items for Staff.

**Architecture:** Delivery A2 of the `staff` module (`apps/server/internal/staff`, schema `staff`, `openapi/staff.yaml`, `apps/staff/frontend`), on top of A1 as merged in PR #135 (main `53ab282c`). One migration for this delivery, `00043_staff_records.sql`: `document_categories`, `documents`, `object_deletions` — **no column is added to `people` or `settings`** (they carry every column since A1; the retention and threshold columns reach the contract now). The module gains its first object-store use (scope `staff`), its first worker (`staff-retention`), its first config keys and its first `Workers` slot. Absence (B) and accounts (C) are NOT in this plan: the payroll export ships without leave and absence columns, `/stats` without the absence figures, attention without the absence and account items, and health documents are erased on an end-of-employment schedule until B brings the sick case.

**Tech stack:** as A1 — Go (pgx v5, sqlc, goose, oapi-codegen strict server), PostgreSQL, `internal/storage`, React 19, Mantine, TanStack Router + Query, Vitest, Bun.

**Spec:** `docs/superpowers/specs/2026-10-11-staff-foundation-design.md` (revision 3) — delivery A2: §1 (A2), S14, S15, S16, S18, S19, S20, S21 (the erase's use of `payload_classes`), §3.1 (the class column), §3.6 (`documents`, `document_categories`, `object_deletions`, `settings`' retention and threshold columns), §4 Erase and Locking, §5, §6 (Documents, Data, Dashboard, People's `/personal-data`, `/legal-hold`, `/reassessed`, Me's `/documents` and `/export`, Settings' `/thresholds/{key}/acknowledge`), §7 (the Documents tab, Settings' data operations, My page's documents and download, the host's dashboard items), §8.5–8.7, §9, §10, §11 readings 9, 10, 31. Research §4.9 (retention), §4.10 (the thresholds), §4.8 (OTP).

## Readings of the spec

1. **The object store is a call out like the directory**: three checked accessors, the hook refusing them inside any transaction; the object written before the transaction and removed after a refusal (the receipt pattern).
2. **At most 200 documents per person** — the spec names no bound; a bound keeps one HR account from filling a volume through a loop, with the rate limit as the second guard.
3. **Health documents are erased on the end-of-employment schedule in A2** (`healthRetentionDays` after the end), since no sick case exists yet; B moves them to the per-case schedule the spec states.
4. **The A erase nulls the pay columns and queues the A documents after five years past the end year**, as S15 says; nothing is kept in a side table — the payroll exports already made are the record.
5. **A signed contract document sets `contract_signed_at`** on the employment covering its `signedAt` when the employment has none; typing the date stays possible.
6. **A rehire of an erased person is `POST /people/{id}/employments`** on the erased record, which clears `erased_at`; the creation form warns through `GET /people/similar-erased` and offers the rehire instead of a duplicate.
7. **Every write to an erased person answers 409 `person_erased`**, except the legal hold and the rehire.
8. **The retention state the UI shows comes from a `retention` block on `GET /settings`** (pending deletions, the last run's instant and counts), not from `/stats`.
9. **The import creates the first employment from optional columns on create only**; an update never touches employments; the import template documents both column sets.
10. **The export shapes columns by permission and never carries the sealed values**; `nationalIdOnFile` is a yes/no column.
11. **The failed-rows file is built in the browser** from the tally, as customers' is.
12. **The payroll CSV's headers are English and Title case** (the Expenses style), the codes Skatteetaten's; the leave and absence columns arrive with B appended to the right of the row.
13. **The `payroll_exported` event carries the SHA-256 of the file**, installation-level, written after the snapshot.
14. **The personal-data export is one in-memory JSON document** in one snapshot (customers' precedent), not a streamed or asynchronous job; a person with thousands of events still fits.
15. **`/me/export` omits the sealed values and HR notes**; everything else of the person's own is in it.
16. **The reassessment item derives from `erased_at` + 12 months**; nothing is scheduled on the row.
17. **The OTP threshold test is "two people at ≥ 75 %, or one at ≥ 75 %, or ≥ 20 % positions summing to two årsverk"** — the owner flag is not modelled, so "one non-owner" reads as "one"; the item says so.
18. **The thresholds are acknowledged per key**, once; a later crossing after the headcount fell below and rose again shows the item again only if the acknowledgement predates the previous drop — simpler: acknowledgement is permanent per key (the company has the routine); a reading the owner may want otherwise.
19. **The worker's "once per business day" is idempotence, not a marker**: a second cycle finds nothing to blank; the ledger runs every poll.
20. **Worker mode builds its own object store from config**, as Communications does, with a deferred error so the worker starts without storage.
