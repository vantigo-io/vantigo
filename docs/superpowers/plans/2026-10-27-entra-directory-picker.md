# Entra phase 2, delivery B — the directory picker: implementation plan

> **For agentic workers:** implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an Owner connects an existing user to the provider by picking their account from the tenant rather than typing a principal name, and connects a whole workspace in one review: Vantigo proposes, for every user not yet connected, the one directory account that matches them exactly, and *Connect selected* announces each chosen pair.

**Architecture:** the Entra module gains two Owner reads against Microsoft Graph — a directory search and the exact matches. What the matches need of identity (the unconnected users' addresses and employee numbers, and who already holds a directory key) comes through a new identity-provided port, `contracts.SSOConnections`, gated by identity itself (module-boundaries rule 12). The connect itself stays identity's `POST /api/v1/identity/owner/users/{id}/sso-link` from delivery A, called once per chosen pair by the host: no new write, no migration. The picker and the review are `@vantigo/entra-ui` components the host composes into the Users screen (rule 7). Branch `feat/entra-directory-picker`, cut from `main` at `ebcb0ab8`.

**Spec:** [`docs/superpowers/specs/2026-10-24-entra-link-existing-users-design.md`](../specs/2026-10-24-entra-link-existing-users-design.md), delivery B and testing B; L5 for the modal the picker drops into.

## Plan readings

The spec names the endpoints and the rule; these are the choices it leaves to the plan.

1. **Entra reads identity through a port, never its tables.** The matches need each unconnected user's address and employee number, both identity's (`identity.users.email`, `employee_number`), and `contracts.UserDirectory` deliberately hands out no address but a `Holder`'s, for mail. A new single-provider port, `contracts.SSOConnections`, provided by identity (`Module.SSOConnections`, `Deps.SSOConnections`, set by Compose as `Accounts` is; Workers does not need it), answers two reads:
   - `Unconnected(ctx) ([]ConnectCandidate, error)` — every user who is not pending, has no link under the configured issuer and no announced link under it, the caller excluded (an Owner connects themselves by signing in, L2); `ConnectCandidate{UserID, Email, EmployeeNumber, Disabled}`. OIDC off answers an Owner `contracts.ErrSSONotConfigured` (changed in task 2 from the empty list first planned: not configured must not read as nobody left to connect, and the matches answer it 409 `sso_not_configured`); `KeyHolders` still answers nothing.
   - `KeyHolders(ctx, keys []DirectoryKey) ([]KeyHolder, error)` — for each object id or principal name, who already holds it under the configured issuer: an announced link (`expected`, with the user), a SCIM mapping (`mapped`: `userName` equal to the principal name, or `externalId` to the object id, with the user), an announced account (`account`, Staff's, no user).
   It is **provider-gated**: identity checks the request in `ctx` against `policy:Owner+OwnerManagement` through its own access and answers nothing — not an error — to anyone else or to a context with no request. The address is for matching and never leaves the Entra module: not on the wire, not in a log, not in an event.
2. **An OIDC link cannot be attributed to a directory account.** `oidc_links` holds the token's `sub`, which Graph never returns (spec reading 1). A hit is therefore shown as held only by what names its keys — an announcement or a SCIM mapping — and an account whose person signed in already is not marked. That user is not a candidate either (they are linked), so the matches never propose them; the search may show their account unmarked, and identity's `sso_link_taken`/`account_linked` still refuse what must be refused.
3. **The search.** `GET /api/v1/entra/directory/users?q=` — `q` trimmed, 2 to 100 characters, else 400 `invalid_request` with the field. Graph: `GET /users?$search="displayName:q" OR "mail:q" OR "userPrincipalName:q"&$select=id,displayName,mail,userPrincipalName,employeeId,accountEnabled&$orderby=displayName&$top=25&$count=true` with `ConsistencyLevel: eventual`; a `"` or `\` in `q` is removed before it is quoted. Each hit carries `holder` from `KeyHolders`. At most 25 hits; the picker says to narrow the search when 25 come back.
4. **The matches.** `GET /api/v1/entra/directory/matches` reads `Unconnected`, then the tenant in chunks of 15 values: `mail in (…)`, `userPrincipalName in (…)` and, for the candidates holding one, `employeeId in (…)`, each with `ConsistencyLevel: eventual` and `$count=true`. A candidate is **proposed** only when every key that matched points to one and the same account — address equal (case-insensitive) to the account's mail or principal name, employee number equal (trimmed, case-insensitive) to its `employeeId` — and that account is neither held (`KeyHolders`) nor the single match of another candidate. Everything else is left out: no fuzzy match, no guess between two. Each proposal answers `{userId, account, matchedBy: [mail|userPrincipalName|employeeId]}`; the answer also counts the candidates (`candidates`) and the ones left out as `ambiguous` (several accounts, or one account for several users). At most 1000 candidates are read, in identity's order; `truncated` says when more exist.
5. **Access and limits.** Both reads are `policy:Owner+OwnerManagement`, like the connection's writes, since they read the whole tenant and identity's addresses. Rate limits: the search `entra-directory`, 60 per client address a minute (a debounced picker); the matches `entra-matches`, 6 a minute. Refusals: 503 `credential_invalid` / `tenant_unreachable` as the licences read answers them (`credentialFor`, `tenantUnavailable`), 503 `throttled` when Graph throttles twice, 409 `sso_not_configured` from the matches when OIDC is off (nothing to connect under).
6. **The fake Graph** (`internal/entra/graphtest`) learns `$search` over the three properties (case-insensitive substring per quoted clause, `OR`), `$top`, `$orderby=displayName`, and `$filter` of the form `<property> in ('…', …)` for `mail`, `userPrincipalName` and `employeeId`; it answers 400 `Request_UnsupportedQuery` without `ConsistencyLevel: eventual` on a `$search`, as Graph does.
7. **The picker.** `@vantigo/entra-ui` exports `DirectoryPicker` — a searchable select over the search endpoint (debounced 300 ms, from two characters), each option the display name, the principal name, the employee id when set, *Disabled* when the account is, and *Awaiting another user*/*Provisioned to another user*/*Announced by Staff* when held — answering `{objectId, userPrincipalName}`. The host's connect modal (L5) shows it when the `entra` module is enabled, above the typed principal name, which stays (filled by the pick, editable, and the only field while the module is off or the directory cannot be read); a pick fills both keys, so the announcement names the object id too.
8. **The review.** `@vantigo/entra-ui` exports `DirectoryMatches` — the proposals as a list (the user's name and address beside the account's display name, principal name, employee id, enabled state and what matched), each with a checkbox, all checked but a disabled account's — and *Connect selected*, which calls a host-provided `connect(userId, {objectId, userPrincipalName})` one pair at a time and marks each row connected or refused in the Owner's words. The host opens it from a *Find matches in the directory…* button on the Users screen, shown while the SSO column is and the module is enabled, passes the users it already holds for the names, and `announceSsoLink` as `connect`, then refreshes the users. entra-ui calls only Entra's endpoints; identity's call is the host's.
