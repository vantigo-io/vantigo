### Implementation notes

Recorded as the tasks landed; where they change a later task, that task's text is edited in place too.

- **Task 2 — `pay/qrsvg`.** Task 2 created `internal/payments/qrsvg` (`Render(text) (string, error)`: the code's modules as `svg`/`rect`/`path` only, never the encoded text) and promoted `github.com/boombuler/barcode` to a direct `go.mod` dependency — in Task 2, not Task 6. Task 6 imports `pay/qrsvg` for `payLink.qrSvg` and does not create `inv/qrsvg.go`. Every QR is shown as `<img src="data:image/svg+xml;base64,…">`, never inlined.
- **Task 2 — the on-site QR.** The Vipps adapter asks for `qrFormat` `TEXT/TARGETURL` and renders the QR locally with `pay/qrsvg`; it never fetches an image from a URL an answer names. Reading 10's "the on-site QR is Vipps' own SVG" is replaced by "rendered locally from Vipps' `TEXT/TARGETURL`".
- **Task 2 — what `pay/` imports.** The standard library, `srv/buildinfo` and `pay/`'s own packages; `pay/qrsvg` alone also imports `boombuler/barcode` (`TestPayments_Purity`). depguard's `test-fakes` rule refuses `pay/vipps/vippstest` in any non-test file. The Global Constraint on module boundaries is adjusted accordingly.
- **Task 2 — a create's conflict.** A 409 is never a definitive create refusal (`IsDefinitiveCreateRefusal` is true only for refused keys, a request never sent, or a 400 naming a code); Vipps' 4150, 4020 and 4010 are `ErrConflict` on any 4xx. On 4150 or 4020 the adapter reads the payment back and answers it as created only for a non-QR flow, with the same amount and currency, in state `CREATED` or `AUTHORIZED`; everything else — a QR above all — is "outcome unknown", and the caller polls the reference (an on-site QR attempt may be abandoned and made again). Capture codes 6260/6280 are capture failures only on a 400, and are not final: nothing was taken and Vipps asks for a retry (Task 8 retries).
- **Task 4 — availability is `paymentsAvailable`, never a switch alone.** `paymentsAvailable(ctx, q)` (`inv/payment_settings.go`) judges `INVOICES_VIPPS_ENABLED`, a credentials row present and not rejected, `PUBLIC_BASE_URL` for pay links, and the settings' two booleans; meta reads it on the pool, and every later path that offers Vipps reads it through its own transaction's queries and gates on it — Task 6's link at issue and on demand on the send, Task 7's create re-reading under the invoice's lock (m15: the switch, the refusal and `PUBLIC_BASE_URL` re-judged there, not only `pay_links_enabled`/`on_site_payments_enabled`), Task 10's on-site request. A setting left on comes back into service when good keys are stored again, with its kontantsalg acknowledgement kept (`A/payments.md`).
- **Task 4 — the credentials' version.** `providerCreds` carries `version`, the credentials row's `updated_at` the provider was built from (every PUT moves it). A refusal is recorded and a verify's `ok` clears one only while the row is still that version (`MarkPaymentCredentialsRejected`/`ClearPaymentCredentialsRejected` take `@version`). Task 7's create compares `providerCreds.version` with the row it reads `FOR SHARE` under the invoice's lock and, on a mismatch, refuses with a retryable 503 `payments_unavailable` — the provider was built from keys a PUT replaced.
- **Task 4 — the first PUT.** With no credentials row the PUT inserts with `ON CONFLICT (id) DO NOTHING`; meeting a concurrent first PUT's row it runs once more on the locked path (`UPDATE … WHERE id = 1` under `FOR UPDATE`), so a sales-unit change is never written unjudged (`TestVippsCredentials_TwoFirstPutsRace`).
- **Task 5 — the quick invoice's clock.** The quick invoice reads the clock once for the draft's defaults and once in `issueLocked` after the counter, as the issue does; `now` is not passed into `issueLocked`. Delivered on day D and waiting on the counter across Oslo midnight, it is issued and handed over on D+1 (`TestQuickInvoice_AcrossOsloMidnight`). The clock rule above says so.
- **Task 5 — a merge in the window.** After its commit the quick invoice reads the billing profile again and, when the customer was merged away meanwhile, moves the document to the survivor under its own lock (`quickFollowMerge`, `RepointQuickInvoice`: the customer id alone). An erase in the window refuses nothing — the manual delivery's parent trigger blanks the note, it does not refuse — so there is no erase refusal to map.
- **Task 5 — a quick invoice's request id.** `InvoicesQuickInvoiceRequest.requestId` (a UUID) is kept in `invoices.quick_requests` (00046, amended: a table of its own, not a column on the invoice), inserted right after the draft. The same id and body again answers 200 with the first's invoice, running nothing again; another body is 409 `request_id_reused`. **Task 10:** a replay never makes a second on-site payment request — `payOnSite` is honoured only by the request that issued the invoice, and a replay answers that invoice and, from Task 10, reports its live on-site attempt (read only, never created) as `paymentRequest`, so a retrying client knows whether a QR already exists — never a new one.
- **Task 4 — the switch-off is a 503.** `payments_unavailable` is a 409 only without credentials; with Vipps switched off on the installation or keys that cannot be opened it is a 503 (`InvoicesConflictProblem`'s description says so).

- **The lock rule (MB rule 10, `inv/server.go:102-118`):** *no call that takes its own connection or leaves the process while a transaction holds locks.* A provider call (`payments.<op>`) leaves the process; it is never made inside `withLockedTx` and always goes through `contractscalls.go`'s `noteContractCall` — the harness fails a test on a locked call. The credentials are read and opened on the pool **before** each provider call; whatever a decision under a lock needs from the provider was learned before the transaction (the attempt row carries it).
- **The lock order (D18's 4C rows, as this plan reads them):** *own row first, then invoices in descending id, never the reverse.* An attempt's create: the invoice `FOR UPDATE` (its pay link and `payment_settings` re-read under it, unlocked — m15), then the credentials row `FOR SHARE` (reading 8), then the attempt inserted. The worker's claim is one `FOR NO KEY UPDATE SKIP LOCKED` statement on the attempt, outside the helpers and the seam (m11). The capture decision and the registration: the attempt `FOR NO KEY UPDATE` (reading 7), then its invoice. A cancel, a release, an abandon, an on-site cancel, a webhook nudge: the attempt alone. A pay link made on demand: the invoice (the link inserted); revoked: the invoice, then the link `FOR NO KEY UPDATE`. The issue and the quick invoice: the document (locked, or inserted and so held), settings `FOR SHARE`, the counter, as today; a pay link and a manual delivery inserted. A credentials `PUT`/`DELETE`, a webhook registration's store: the credentials row `FOR UPDATE` alone (the live attempts counted under it). A payment-settings `PUT`: its row `FOR UPDATE` alone. A day's reconciliation: none (an insert). The erase: the person's documents (customers' transaction), then their live pay links. **No path locks an invoice and then an attempt**, nor an attempt and then the credentials row. Every new lock goes through a helper in `inv/locks.go` reporting to the lock-order seam (`lockTaken`, `inv/locks.go:22-31`).
