# Entra phase 1, delivery B — the announced account and the provisioner slot: implementation plan

> **For agentic workers:** implement this plan task by task, one implementer per task and a reviewer after it, never in the same context. Tasks 3 and 4 get a security-focused reviewer (an announcement adopts a user the provider creates, with no Owner in between; a pass is a credential). Steps use checkbox (`- [ ]`) syntax for tracking. No agent commits; the coordinator commits per task group.

**Goal:** identity accepts the SCIM enterprise extension and lets Staff **announce** the account an external provider will create for a person, so that the user the provider's SCIM push or the person's first sign-in makes is adopted as Staff-managed, numbered and not pending, with no Owner in between; Staff carries the account's authority **per person** (`local` | `external` | `entra`, the installation's default a setting) in place of the installation-wide mode; the platform gains the many-provider slot `contracts.IdentityProvisioner` through which Staff will drive an external directory, with a fake provider in `modtest` that proves the slot, the worker's third column and the attention items before the Entra module exists; HR sees both links on the person's Account tab with the pass and the directory profile; and the installation chooses, under Settings, which directory fields the provider writes.

**Architecture:** `contracts` (the slot's interface, `AccountProvisioning.Expect`/`Unexpect`, the kind on the spec), `module` (the slot on `Deps` and `Module`, collected from enabled modules by `Compose` and `Workers`), `modtest` (the fake provider), `identity` (D3, D4), `staff` (D5, D7, D8 — the decision table's third column, the provider link, the settings, the Account tab's endpoints), `apps/staff/frontend` (the Account tab and the Settings cards), the docs. Branch `feat/staff-provisioner-slot`, cut from `main` at `0944879b` (A merged), the PR against `main` (see `stacked-prs-per-phase`: no stack, A has landed). **Two migrations**, one file per schema (`schema_test.go`): `00059_identity_expected_accounts.sql` and `00060_staff_account_kind.sql` (00058 is the highest on main), each with its pin test in `internal/db`. No provider module, no new permission, no new worker: Staff's accounts worker drives the provider link under the claim it already holds.

**Spec:** [`docs/superpowers/specs/2026-10-19-entra-design.md`](../specs/2026-10-19-entra-design.md) D3–D8, its deliveries table (B), testing (B), readings 3 and 4; the research [`2026-10-19-entra-module.md`](../research/2026-10-19-entra-module.md) §3.7 (what Entra sends back: `mailNickname → externalId`, `oid`), §5.3 (the announced account, `ReplaceUserID`), §7.1–7.2 (the slot's shape, the kind per person), §7.4 (the directory profile's table).

## Readings of the spec

1. **The kind travels on the call.** D5 keeps `Mode()` for the `external` kind's rule, but identity's `Prepare`, `Activate` and `Update` today switch on the mode, and an `entra` person in an installation whose SSO row is on would get no roles (federated gives none) while a `local` person in it would be created as a pending user — the per-person decision has to reach identity. `AccountSpec.Kind` and `ActivateOpts.Kind` carry it; "" keeps the previous release's behaviour for a worker on the old binary.
2. **`Key()` beside `Provider(ctx)`.** Composition needs the key with no context and no network to refuse two providers with one key; the status still comes through `Provider(ctx)`.
3. **"The roles once" needs a marker.** An adopted user arrives enabled (SCIM `active`, or the sign-in that made them), so "the Activate that enables them" never comes; `users.provisioning_roles_at` is where identity remembers that Staff's set was given, which also records it for the local path.
4. **The kinds are seeded by Staff, not the migration.** `schema_test.go` forbids a staff migration naming `identity.system_settings`; Staff reads `Mode()` through its accessor at mount and seeds under the settings lock, once, the way A imported the environment.
5. **The announcement's UPN and object id are not unique.** Two announcements with one UPN would be Staff's bug; the match takes the newest and the plan does not add a refusal the design lacks.
6. **`Expect` for a number already held by a managed, non-pending user records nothing** and answers nil: the account has arrived (or an Owner adopted it) and the worker's `Prepare` finds it; an announcement would only raise `accountNotArrived` later.
7. **Three calls per column.** D7 says "at most three per claim"; a fresh `entra` joiner's first claim needs `Prepare`, `Expect` and the identity `Prepare`, so the bound is three provider calls (the announce among them) and then three identity calls, under one claim and one lease.
8. **The issuer is identity's.** Staff knows no OIDC issuer; `Expect` leaves `Issuer` empty and identity fills it from its SSO row when OIDC is on, so the `oid` match checks the issuer the sign-in actually completes under.
9. **The directory profile is shown to whoever reads the Account tab** (the person included): it is their own data as the provider would see it, and nothing in it is HR's alone.
10. **The attention items are named for Entra** (`accountAmbiguousInEntra`) as the design names them, though the codes and the slot are generic; a second provider would add its own items.
